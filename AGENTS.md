<architecture_boundaries>
- **Platform Host Boundary:** `app/` owns the Android host and protected Android Gateway. `desktop/` owns the Desktop host and Windows product identity/packaging. Shared behavior belongs in KMP modules only when it is valid for both hosts; platform-specific branding, lifecycle, notifications, installers, and integration adapters stay in their platform host.
- **Track Impact Review:** Before changing `commonMain`, shared resources, navigation, service/database contracts, or a shared feature, identify the Android and Windows effects. Preserve the Android green brand and Android IPC behavior while evolving Windows, and preserve the Windows blue brand and desktop startup/packaging behavior while evolving Android.
- **Project Namespace:** New project-owned code must use `com.ntsocial.meshlink.*`. Do not introduce new `org.meshtastic.*` or `com.geeksville.mesh` project packages.
- **Protocol Boundary:** Keep generated upstream Meshtastic protobufs under `org.meshtastic.proto`. Do not edit `core/proto` unless the user explicitly requests upstream protocol/submodule work.
- **Semantic Meshtastic Names:** Existing identifiers such as `MeshtasticNavDisplay`, `MeshtasticNavigationSuite`, `MeshtasticBleConstants`, and `MeshtasticDatabase` may remain when they describe upstream protocol, device, database, or shell semantics. Do not perform cosmetic class renames without a scoped migration plan.
- **Android Gateway Boundary (implemented v1 + additive v2):** New Android NTsocial integrations must use the protected Gateway IPC. Keep every v1 path, column, command, and value immutable. `NtsocialGatewayService`/AIDL remains a deprecated compatibility adapter only; do not add features that bind it or directly bind `IMeshService`. New outbound traffic uses `PRIVATE_APP / port 256`; legacy `497` is receive-only compatibility. These Android ContentProvider/broadcast/AIDL mechanisms are not a Windows IPC design.
- **Windows Integration Boundary (not implemented):** `NTsocial MeshLink` Windows is currently an independent Meshtastic desktop client intended to serve the separate `NTsocial_Windows` project in a future phase. Define and review an explicit Windows IPC/protocol, authentication, lifecycle, versioning, and threat model before integration work. Do not silently reuse Android IPC, expose internal database/service objects, import proprietary parent-App business logic, or describe branding/packaging as functional `NTsocial_Windows` interoperability.
- **Application Version Governance:** LiberaNt LLC and the NTsocial team own NTsocial MeshLink release/version policy. The radio-reported upstream `min_app_version` remains an ingested protocol/database compatibility field, but must not be compared with the NTsocial MeshLink `VERSION_CODE`, used to label MeshLink outdated, force a device deselection, or direct users to upstream Meshtastic App update channels. Radio-firmware compatibility checks are a separate boundary and remain supported.
- **Windows Packaging Identity:** Windows uses display/package name `NTsocial MeshLink`, vendor `LiberaNt LLC`, menu group `NTsocial`, application ID `com.ntsocial.meshlink.desktop`, and stable upgrade UUID `6784A2DD-CE59-518B-AA15-C26302D6FA85`. Preserve the UUID for in-place upgrades of this Windows product. Keep macOS/Linux metadata and icons unchanged unless a task explicitly expands platform scope.
- **Windows Brand Provenance:** `C:\Users\cth\Documents\GitHub\NTsocial_Windows` is a read-only brand reference. Only explicitly authorized brand assets may be copied; never modify that repository or import its code, secrets, credentials, or unrelated/proprietary data. Record source paths, source commits, and SHA-256 hashes in `desktop/BRANDING_ASSETS.md`.
- **Gateway Provider:** The authority is `${applicationId}.gateway`; immutable v1 read-only endpoints are `/v1/status`, `/v1/envelopes`, `/v1/nodes`, and `/v1/channels`. Additive v2 read-only endpoints are `/v2/status`, `/v2/channels`, and bounded `/v2/message-changes?after=&limit=`. v2 exposes only sanitized Meshtastic catalog/native broadcast-text facts: never raw PSKs, raw radio configuration, precise location, or canonical NTsocial history. Encrypted source-channel IDs are domain-separated SHA-256 digests of resolved PSKs; CLEAR channels retain the existing deterministic public identity rules. `/v2/message-changes` exposes only rows whose stable identity was captured at insertion and never derives an old row from the currently configured slot. Do not add unversioned endpoints, Provider mutations, or selection/sort semantics.
- **Gateway Cursor Domains:** `history_epoch` is a durable random value in the active per-radio Room database. Initial creation and whole-history clear persist it transactionally; switching databases exposes the target database's stored epoch rather than rotating on every switch. `not-ready` is transient and must not be persisted or treated as a reset. The current active publisher has a known defect: `getGatewayHistoryState()` captures the epoch once per subscription, so a whole-history clear can publish sequence zero with the old epoch until the history flow is resubscribed, for example by an active-database switch or process restart. Do not claim live clear/reset correctness until this is fixed and device-tested. `radio_generation` is opaque random process state; it rotates on process restart and any `ChannelSet` inequality, potentially including LoRa/config differences not exported in the catalog, invalidates every route token, and must never be a ChannelSet/config digest.
- **Native Text Insertion Cursor:** `/v2/message-changes` is an insertion cursor, not a general change feed. It includes only unfiltered broadcast `TEXT_MESSAGE_APP` rows inserted by live ingress, Store & Forward router-text broadcast, MeshLink's own native send, or accepted Gateway `SEND_CHANNEL_TEXT`, with both stable identity columns captured at insertion. Gateway-originated rows may additionally expose nullable `origin_client_message_id` for reliable parent own-echo correlation; it is local metadata and never enters the Meshtastic packet/protobuf. DMs, reactions, filtered rows, state/control traffic, port-256 NTsocial overlays, and upgraded nullable legacy rows are excluded; updates and deletes create neither a new sequence nor a tombstone. A nullable legacy row must never be recomputed from current slot/config state because slot reuse could assign channel A's message to channel B. `change_seq` is the monotonically increasing Room packet `uuid` within one database, not a message ID, timestamp, delivery state, or cross-database order. The v2 status high-water uses the same stable-only predicate, so it never advances to an unexportable nullable row. The default page is `after=0&limit=100`, the maximum limit is 200, and negative/repeated/unknown parameters are rejected. Consumers must pair the cursor with a real epoch, restart at zero on epoch change, advance to the maximum returned sequence, and retry without mutating durable cursor state while status is `not-ready`.
- **Room 43 Gateway Schema:** Auto-migration 41-to-42 adds nullable `gateway_source_channel_id` and `gateway_source_message_id` packet columns, non-unique lookup indexes, and the `gateway_metadata` table. Auto-migration 42-to-43 adds only nullable `origin_client_message_id`; it does not backfill or alter serialized packet/protobuf data. Rows that remain without captured stable identity stay available only to MeshLink's internal/local compatibility views and are not Gateway v2 history. Duplicate Room rows may share a stable source-message ID, so clients dedupe by exported identity rather than assuming database-row uniqueness. Generated schemas/unit gates are not retained proof of real on-device migrations.
- **Gateway Commands:** A parent App obtains an in-memory, request-bound, single-use capability with a 30-second TTL from the Provider, then sends an explicit `com.ntsocial.meshlink.gateway.COMMAND`. Android 8-13 relies on the consumed capability; Android 14+ also verifies the broadcast sender UID, package, and certificate. Never trust caller-supplied package names or ports, and never use implicit broadcasts.
- **Gateway Routes and Idempotency:** Each v2 catalog query issues a random 32-byte, in-memory route token with a 120-second TTL. It is reusable until expiry but bound to the exact verified caller UID/package, source-channel ID, captured slot, and current radio generation; process restart loses it. A routed command does not accept or trust a caller channel index. `client_message_id` accepts exactly 32 hexadecimal characters and is canonicalized to uppercase. The durable ledger is capped at 256 insertion-ordered records, keyed by caller package plus canonical ID, and has no TTL; reuse with a different request fingerprint is an idempotency conflict.
- **Routed Command Commit Order:** Both routed v2 sends first durably commit the PENDING ledger reservation, then insert or exact-content-check the deterministic packet ID in Room, await unique WorkManager `REPLACE` admission, commit ACCEPTED, and only then emit `COMMAND_ACCEPTED`. If the final ACCEPTED ledger commit fails after Room/WorkManager success, `queue_failed` does not prove the packet was unscheduled; retry the same client ID. A crash between local admission and durable acceptance can still cause a physical RF duplicate, so this is restart-stable local idempotency, not exactly-once radio delivery.
- **Gateway Events:** `com.ntsocial.meshlink.gateway.EVENT` is explicitly package-scoped and metadata-only. It may carry event type, URI, request ID, packet ID, or rejection reason; it must never carry message bytes, destinations, precise location, PSKs, tokens, or radio configuration. A client re-queries the Provider after an event.
- **Trusted Pairing:** The in-process UID/package/certificate verifier is authoritative. Debug and release MeshLink builds accept only `com.ntsocial.android.debug` with the stable team-debug signer and `com.ntsocial.android` with the approved release signer; host and caller no longer need the same build type or signer. Ordinary signature-permission grant is not sufficient by itself. Private keys remain outside the repository. A parent package or signer change requires a synchronized update to verifier rules, known-signer resources, NTsocial package visibility/trust, and both build configurations; never broaden this to arbitrary installed Apps or an unpinned machine-generated debug signer.
- **Outbound Transport Contract:** v1 external commands accept only a validated complete `NM` envelope, unchanged, on the currently ready canonical default RF index; acceptance is the synchronous `CommandSender` return. v2 `SEND_NTSOCIAL_ENVELOPE_TO_ROUTE` accepts the same envelope only with a current caller-bound `source_channel_id`/`route_token` pair and uses the slot captured by that route. Both overlay paths use `PRIVATE_APP / port 256` and cap the complete envelope at 180 bytes. Additive v2 `SEND_CHANNEL_TEXT` uses the same capability, caller-bound route, radio generation, client-message ledger, Room, and WorkManager commit order, but accepts only nonblank text at most 180 UTF-8 bytes and constructs an unfiltered broadcast `TEXT_MESSAGE_APP` row for MeshLink's normal channel UI. Its dynamic route revalidation, existing-row check, insertion, and queue admission are serialized by the repository's native-text owner so concurrent retries cannot create duplicate chat rows. It never accepts a destination, caller slot, port, packet ID, or encoded packet. Every accepted result is local admission only, never firmware airtime or remote receipt. `497` is never an outbound command port.
- **Gateway Identity:** Every encrypted channel derives `source_channel_id` only from a domain-separated SHA-256 digest of the resolved `ModelChannel.psk`; configured name, slot, role, numeric channel ID, and install state are excluded. Meshtastic shorthand PSKs 1 through 10 are resolved before hashing, so shorthand and their full-key forms converge; `security_class` is likewise based on the resolved PSK (`CLEAR`, the ten `WELL_KNOWN` keys, or `CUSTOM`). CLEAR compatibility is byte-for-byte retained: a nonzero `ChannelSettings.id` uses the existing unsigned numeric-ID domain, while a zero-ID CLEAR channel uses the existing canonical resolved-name plus empty-key domain. Existing rows that already captured an older source ID retain that exact partition; do not alias or rewrite them. `source_message_id` is the uppercase first 32 hex characters of a domain-separated SHA-256 over stable channel ID, normalized sender node ID, unsigned packet ID, port, and payload hash; use it for import dedupe even when duplicate Room rows exist. Never export `!local` as a durable author: normalize local outgoing native text to the stable own-node ID before identity capture, and fail closed until that ID is known.
- **Gateway Identity-Key Storage:** The obsolete install-local legacy HMAC provider and its Android/Desktop dependency-injection seams are removed. An old private preference left by an upgraded install is inert and is neither read nor exported. Desktop still compiles the shared PSK-derived identity/capture path but does not expose the Android Provider contract or a Windows Gateway IPC.
- **Cache and Acceptance Semantics:** The bridge cache is transient, in-memory, and bounded to 128 envelopes; NTsocial remains the social UX and canonical-history owner. For routed v2 commands, `COMMAND_ACCEPTED` means Room and platform retry work were committed locally; it does not mean the firmware accepted RF airtime or any remote radio/NTsocial peer received it. Overlay sends do not appear as ordinary Meshtastic native-text messages.
- **Node Policy:** `rebroadcast_mode = ALL` is an NTsocial Node Policy applied with clear user consent and verification, not a silent forced configuration.
- **Channel Model:** `source_channel_id` is the durable radio-side identity and must be treated as opaque. Slot/index is only a mutable locator. MeshLink owns neither a parent NTsocial logical `channelId`, group membership, nor logical binding; many parent logical channels may intentionally route through one source channel.
- **Parent Channel Policy:** Gateway v1 validates only the canonical ready default index. Gateway v2 ignores any caller notion of channel index and resolves any current configured catalog slot exclusively from the caller/source/generation-bound route token. The parent may automatically create a dedicated logical projection for every catalog row; that must not erase the separate opt-in workflow that manually binds an ordinary parent channel to a source channel.
- **Built-In NTsocial Channel:** NTsocial MeshLink bundles the canonical public NTsocial Meshtastic channel and automatically ensures it is registered after node-database readiness. Provisioning may rewrite only a slot whose name equals the canonical NTsocial name case-insensitively or whose PSK exactly matches, including primary; otherwise it appends at the current settings-list size when below the radio maximum (primary only for an empty list, secondary thereafter). `NO_SPACE` performs no channel write and must not mutate an unrelated slot. Applying default LoRa config and then writing the channel are sequential radio commands, not a transaction: if the second command fails, an already accepted LoRa-config change may remain. This automatic registration does not require a user confirmation dialog.
- **LoRa Config Preservation:** Built-in NTsocial channel provisioning may apply the QR LoRa/RF config only when the radio is effectively unconfigured, such as missing LoRa config or `region == UNSET`; never overwrite an already configured region/frequency/preset.
- **LoRa Payload Policy:** Do not route image bytes, voice bytes, or PTT media over LoRa. LoRa roadmap payloads are text, state/control, profile/channel snapshots, roster/probe data, chunks, and receipts.
- **Open-Source Boundary:** This GPL fork must not embed closed NTsocial App business logic, private assets, secrets, or production credentials. Protocol/schema/IPC work intended for this Gateway should remain open.

- **Hygiene:** Run `python3 scripts/sort-strings.py` after adding string resources to maintain organization and update the index.
- **Memory Persistence:** Update `.agent_memory/session_context.md` at the end of every session or major task.
- **Bootstrap First:** Run the mandatory bootstrap steps in `.skills/project-overview/SKILL.md` before any Gradle build.
- **Validation Environment:** Use JDK 21 and a valid `ANDROID_HOME`. For local validation, set `JAVA_TOOL_OPTIONS="-Duser.language=en -Duser.country=US"` when tests depend on English resources.
- **Gradle JVM Compatibility:** Root `gradle.properties` intentionally uses `-XX:+UseG1GC`. The currently configured Android Studio JBR 21 reports `Option -XX:+UseZGC not supported`; do not restore `UseZGC` or `ZGenerational` unless the exact build JVM has first been verified to support them.
- **16 KB Native Page Compatibility:** The former osmdroid/GeoPackage native path is removed. After changing any remaining native dependency, audit the produced arm64 APK with `zipalign -c -P 16` and verify every packaged ELF's `PT_LOAD` alignment before device or Play delivery.
- **Navigation Assembly Tests:** Tests that only verify Navigation 3 entry-provider registration should construct the `NavBackStack` and providers directly. Do not launch Robolectric Activity/Compose infrastructure for this contract; it previously caused a one-minute `UncompletedCoroutinesError` cleanup flake under the full parallel baseline despite correct navigation assembly.
- **Plan Before Execution:** Use `.agent_plans/` (git-ignored) for complex refactors.
- **Baseline Verification:** Always run `./gradlew spotlessApply spotlessCheck detekt assembleDebug test allTests` for implementation changes. KMP, flavor, navigation, dependency, or host-wiring changes also require `./gradlew kmpSmokeCompile :app:lintFdroidDebug :app:lintGoogleDebug`. Use `--no-configuration-cache` when cache or stale problems-report issues interfere.
- **Windows Verification:** Windows/Desktop changes require `./gradlew :desktop:test`. Shared UI/KMP or host-wiring changes additionally require the full baseline and KMP/lint command above. Installer metadata, resource, icon, or packaging changes require a complete JDK 21 with `jpackage.exe` and `./gradlew :desktop:packageReleaseDistributionForCurrentOS`; inspect the MSI/EXE names, ProductName, Manufacturer, UpgradeCode, menu group, shortcuts, and icons. Treat output as unsigned unless signing was explicitly configured and verified.
- **Windows Manual QA:** Before a Windows release claim, inspect 100%, 150%, and 200% display scaling; system light/dark themes; background crop and contrast; app bar/navigation/panels; taskbar, tray, and toast identity; the complete three-second splash; and tray re-show without splash replay. Installer coexistence and in-place upgrade claims require an actual authorized install test, not metadata inspection alone.
- **Play Release Verification:** After any Android dependency, manifest, signing, store-facing resource, or release-path change, run `./gradlew :app:verifyGoogleReleaseNoCloudRuntimeDependencies :app:bundleGoogleRelease` in addition to the applicable baseline. Verify the merged-manifest guard, upload certificate, Play app-signing certificate, `bundletool validate`, 16 KB native alignment, App Bundle Explorer contents, and Play-installed artifact; a successful local bundle task alone is never enough.

<rules>
- **Token Hygiene:** Never read binary files such as PNG, MP3, APK, or large non-code resources unless essential. Use file paths to reason about assets.
- **Context Discipline:** Limit context to relevant modules. Do not vacuum the entire codebase for localized fixes.
- **No Lazy Coding:** Do not use placeholders such as `// ... existing code ...`. Provide complete, valid code.
- **No Framework Bleed:** Never import `java.*` or `android.*` in `commonMain`. Use KMP equivalents such as Okio, `Mutex`, and atomicfu.
- **CMP Over Android:** Use Compose Multiplatform constraints. Pre-format floats with `NumberFormatter.format()`. Use `MeshtasticNavDisplay` and `NavigationBackHandler`.
- **Zero Lint Tolerance:** Do not add or suppress new findings; `spotlessCheck` and every
  changed-module Detekt task must pass, and full root `detekt` remains the authoritative release gate.
  The current base is not full-root green because of three pre-existing findings in the unmodified
  `core/ble/src/jvmMain/.../JvmDesktopBluetoothPairingService.kt` (`TooGenericExceptionCaught` and two
  `ThrowsCount`). Record that blocker honestly on unrelated work, and fix it rather than suppress it
  when the file or release gate is in scope.
- **Verify Before Push:** Treat any push as verify-then-push. Check GitHub Actions state before pushing when GitHub context is relevant.
- **Never Touch Protos or Secrets:** `core/proto` is an upstream submodule. Secrets are git-ignored and must not be logged, committed, or exposed.
- **Privacy First:** Never log or expose PII, precise location, private messages, cryptographic keys, tokens, or pairing credentials.
- **Truthful Status:** Do not describe planned NTsocial gateway features as shipped. Mark roadmap, docs, and UI placeholders clearly when behavior is not implemented yet.
- **Attribution Integrity:** Do not remove upstream copyright, license, warranty, or third-party notice text. Do not hand-edit a different Kotlin/KTS/XML header; update the synchronized Spotless/Detekt templates and preserve excluded wrapper, submodule, generated, and third-party headers.
</rules>
